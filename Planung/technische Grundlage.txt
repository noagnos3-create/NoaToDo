# Technisches Fundament — Lokale To-Do-App

> Dieser Abschnitt beschreibt NUR das technische Fundament (auf welcher Basis
> gebaut wird). Die eigentliche App-Idee, Funktionen und Design folgen separat.

## 1. Grundprinzip

Eine **local-first Desktop-App**: Alle Daten und die Logik liegen auf dem
eigenen Rechner. Die App besteht aus zwei Hälften, die zusammen in einem
nativen Fenster laufen:

- **Frontend (Oberfläche):** eine lokale Webseite aus HTML/CSS/JS. Hier lebt
  das gesamte Design. Wird in einer WebView angezeigt.
- **Backend (Logik):** ein Python-Prozess. Hält die Datenbank, redet mit
  Microsoft, verwaltet Zugangsdaten, löst Benachrichtigungen aus.

Zusammengehalten wird beides von **PyWebView**, das die system-eigene WebView
(unter Windows: WebView2) nutzt und kein eigenes Chromium mitbringt. Dadurch
bleibt die App klein und ressourcenschonend.

## 2. Tech-Stack (konkret)

| Schicht | Wahl |
|---|---|
| Fenster / Wrapper | **PyWebView** |
| Backend-Sprache | **Python 3.x** |
| Oberfläche | **HTML + CSS + JavaScript** (vanilla, kein Build-Step nötig). Optional: Tailwind per CDN als Design-Beschleuniger. |
| Lokale Datenbank | **SQLite** (Pythons eingebautes `sqlite3`-Modul) |
| HTTP zu Microsoft Graph | **httpx** |
| Microsoft-Authentifizierung | **msal** (Public Client, Authorization-Code-Flow mit PKCE) |
| Berechtigung (Scope) | **`Tasks.Read`** (nur lesen — passt zum One-Way-Konzept) |
| Token sicher speichern | **keyring** (legt Tokens im Windows Credential Manager ab, nicht im Klartext) |
| Lokale Benachrichtigungen | **winotify** (oder `plyer`) |

## 3. Die Brücke zwischen Frontend und Backend

Frontend und Backend reden über die `js_api`-Funktion von PyWebView:

- Beim Start wird dem Fenster ein Python-Objekt als `js_api` übergeben.
- Im JavaScript ruft man dessen Methoden über `pywebview.api.methodenname(args)`
  auf. Das gibt ein Promise zurück, das den Rückgabewert der Python-Funktion
  als JSON liefert.

**Beispiel-Ablauf:** UI ruft `pywebview.api.get_tasks()` → Python liest die
Aufgaben aus SQLite → gibt sie als JSON zurück → das JavaScript zeichnet daraus
die Aufgaben-Kärtchen. Aussehen vorne, Logik hinten, JSON dazwischen.

## 4. Projektstruktur (Vorschlag)

```
todo-app/
├── main.py              # Startpunkt: erstellt das PyWebView-Fenster, bindet js_api
├── backend/
│   ├── api.py           # die js_api-Klasse (Methoden, die das Frontend aufruft)
│   ├── db.py            # SQLite: Schema, Lesen/Schreiben
│   ├── graph_sync.py    # Sync-Logik gegen Microsoft Graph
│   ├── auth.py          # MSAL-Login, Token-Handling über keyring
│   └── notify.py        # lokale Benachrichtigungen
├── frontend/
│   ├── index.html
│   ├── style.css        # hier lebt das Design
│   └── app.js           # UI-Logik, ruft pywebview.api.*
└── data/
    └── tasks.db         # lokale SQLite-Datenbank (wird automatisch erstellt)
```

## 5. Datenfluss & Sync-Modell (One-Way)

- **Quelle:** Microsoft To Do, gelesen über Microsoft Graph
  (`GET /me/todo/lists` und `/me/todo/lists/{id}/tasks`), nur lesend.
- **Ziel:** lokale SQLite-Datenbank.
- **Richtung:** strikt Graph → SQLite. Lokal hinzugefügte oder bearbeitete
  Aufgaben bleiben lokal und werden **niemals** zu Microsoft zurückgeschrieben.
- **Duplikate vermeiden:** jede importierte Aufgabe wird über ihre stabile
  Graph-`id` identifiziert (Upsert statt blindem Einfügen).
- **Effizienz:** Delta-Queries verwenden, damit pro Sync nur Änderungen geholt
  werden statt jedes Mal alles.
- **Auslöser:** Sync beim App-Start und danach periodisch (Polling, z. B. alle
  paar Minuten). Webhooks gehen bei einer rein lokalen App nicht.

## 6. Offene Designentscheidung (muss festgelegt werden)

Was passiert mit einer **importierten** Aufgabe, wenn sie sich gleichzeitig in
der Cloud (Handy) und lokal ändert? Zwei saubere Optionen:

- **A — Cloud besitzt importierte Aufgaben:** beim Sync überschreibt der
  Microsoft-Stand die lokalen Änderungen an importierten Aufgaben.
- **B — Eingefrorene Kopie:** eine importierte Aufgabe wird einmal kopiert und
  danach von Microsoft nicht mehr angefasst.

(Rein lokal erstellte Aufgaben sind davon nie betroffen — die gehören immer dir.)

## 7. Privatsphäre — was wo bleibt

- **Bleibt lokal:** alle selbst erstellten Aufgaben, alle lokalen Bearbeitungen,
  die gesamte SQLite-Datenbank, die Zugangs-Tokens.
- **Kommt aus der Cloud:** ausschliesslich die aus Microsoft To Do gelesenen
  Aufgaben. (Wichtige Ehrlichkeit: diese Daten liegen ohnehin schon bei
  Microsoft — der Privatsphäre-Gewinn ist, dass nichts aus dieser App je dorthin
  zurückfliesst.)
